# PCB Agent 真实场景测试指南（简版）

这份指南只保留 5 组核心测试。  
每组只看三件事：

- 要做什么实验
- 目的是什么
- 预期效果是什么

重点不是要求每次算法都一定成功，而是看流程能不能走对、状态能不能接住、失败时能不能说清楚。

---

## 1. 混合流程切换测试

### 要做什么

- 先发起一次 BGA fanout。
- 在 fanout 过程中改目标，比如从 `U27` 改成 `U55`。
- 或者在 fanout 过程中直接改口为 reroute，比如说“改为拆线重布，不要继续 fanout”。
- 做完一轮 reroute 后，再说一次“再 reroute 一次”。

### 目的

验证系统能不能在一次对话里灵活切流程，不会卡死在前一个状态里。

### 预期效果

- 改目标后，系统不会直接沿用旧参数继续执行。
- 从 fanout 切到 reroute 时，系统能正确进入 reroute。
- 做完一轮 reroute 后，还能继续第二轮。
- 整个过程中不应出现“状态错乱”“无法继续当前流程”这类错误。

---

## 2. Fanout 灵活状态测试

### 要做什么

- 发起 fanout，等系统生成参数后：
  - 改目标
  - 改参数，比如线宽、线距、算法、模块
  - 说“回到上一步”
  - 最后再“确认”执行

### 目的

验证 fanout 进入确认阶段后，用户还能继续改、退、重来，而不是只能一条路走到黑。

### 预期效果

- 用户修改目标后，系统能重新进入正确的确认状态。
- 用户修改参数后，系统会回显新的 `fanoutParams`。
- 用户说“回到上一步”后，系统能恢复到上一个合理状态。
- 用户最后确认时，即使底层 router 失败，也应该明确返回失败原因，而不是卡住或丢结果。

---

## 3. 前端注入状态恢复测试

### 要做什么

- 由前端直接带上已有的：
  - `selection`
  - `fanoutParams`
  - 或 `routingResult`
- 然后测试：
  - 改目标
  - 改参数
  - 回到上一步
  - 直接确认

### 目的

验证前端如果已经有缓存状态，Agent 能不能直接接住继续，不需要重新完整走一遍流程。

### 预期效果

- Agent 能正确使用前端注入的状态。
- 不会忽略 `fanoutParams`，也不会把流程当成全新任务。
- 用户刷新、返回、恢复后，流程还能继续。
- 最终回复里仍应保留结构化字段，而不是只回普通文本。

---

## 4. Reroute 单轮与切换测试

### 要做什么

- 在前端先框选一段走线。
- 输入“把我框选的线删除后重新布线”。
- 再测试从 fanout 中途切到 reroute。
- 还要测试一轮 reroute 结束后再次 reroute。

### 目的

验证 reroute 能不能形成完整闭环，并且能和 fanout 流程平滑切换。

### 预期效果

- 框选走线后，系统能正确进入 reroute。
- 中间会有“准备上下文”“生成候选走线”等过程反馈。
- 最终应返回结构化结果，例如 `rerouteResult`、`checkReport`、`explanation`。
- 即使外部模型、密钥、DRC 环境没配好，也应优雅失败，而不是直接崩掉。

---

## 5. Reroute 多轮与回退测试

### 要做什么

- 发起一轮 reroute。
- 第一轮结束后再说“再 reroute 一次”。
- 另外再测一次“回到上一步”。

### 目的

验证 reroute 不只是能跑一轮，还能多轮连续执行，并且支持回退到上一检查点。

### 预期效果

- 第二轮 reroute 可以正常进入，不会因为上一轮结束而报状态错误。
- 用户说“回到上一步”后，系统能明确提示已经恢复到上一个检查点。
- 回退后流程还能继续，不会直接废掉。

---

## 统一通过标准

这 5 组测试里，重点看下面 4 件事：

1. 流程有没有走对。
2. 状态能不能接住、修改、回退、重入。
3. 最终有没有稳定返回结构化结果。
4. 环境缺失时，能不能优雅失败并说清楚原因。

如果这 4 件事都稳定，说明这版 Agent 已经具备真实场景联调价值。
